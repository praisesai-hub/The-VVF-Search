# The-VVF-Search: Findings 31–35 Verification and Remediation Report

**Date:** 21 August 2026  
**Repository:** [praisesai-hub/The-VVF-Search](https://github.com/praisesai-hub/The-VVF-Search)

## Executive summary

Findings 31–35 were compared with the current implementation. Findings 31 and 34 were largely already addressed, finding 32 was valid and has been improved with runtime hardware-backed capability inspection, finding 33 was not reproduced in the current source because production key creation fails closed when Android Keystore is unavailable, and finding 35 is not applicable to the current checkout because the database is not constructed with SQLCipher or a passphrase.

The main implementation change is a new `isMainKeyInsideSecureHardware()` API that inspects `KeyInfo.isInsideSecureHardware`. The app should describe the key as **Android Keystore-backed** unless this runtime capability check returns true on the current device.

## Detailed findings

### 31. PIN brute-force rate limiting

The finding is only partly valid against the current repository. `VaultManagerEngine` persists failed-attempt and lockout state, applies a capped increasing lockout duration, and stores lockout timestamps. The compatibility ViewModel also has a cooldown state. This is materially stronger than a basic in-memory verification counter.

The remaining work is validation rather than a safe blind code change. A complete local-attacker threat model should test biometric failure interaction, process restart persistence, elapsed-realtime versus wall-clock manipulation, device reboot behavior, and database/prefs tampering. No claim is made that application-level lockout defeats a privileged or rooted attacker.

### 32. Hardware-backed Keystore capability

The finding was valid. A 256-bit AES key generated by `KeyGenParameterSpec` proves that the key is Android Keystore-managed, but does not by itself prove that the device has placed the key inside secure hardware.

`KeystoreVaultManager` now provides:

```kotlin
fun isMainKeyInsideSecureHardware(): Boolean?
```

The method obtains `KeyInfo` from the Android Keystore key factory and returns `isInsideSecureHardware`. A nullable result represents devices or environments where capability inspection is unavailable. Documentation and UI should use “Android Keystore-backed” as the baseline and only state hardware-backed when this method returns `true`.

### 33. In-memory key fallback

The cited `memoryKeyMap` and raw-key `SecretKeySpec` fallback were not found in the current source. `ensureSecretKeyExists()` throws an `IllegalStateException` when Android Keystore is unavailable, with an explicit message refusing to create a non-persistent vault key. `VaultCryptoSession` is a short-lived holder for an already-authorized data key, not a persistence fallback.

This finding is therefore not reproduced. Tests should inject a fake crypto provider rather than weakening the production Keystore boundary.

### 34. Vault PIN material in SharedPreferences

The finding is mostly addressed. The production vault path constructs a `SecureKeyValueStore`, while `SharedPreferencesKeyValueStore` is retained for explicit test injection and `LegacyEncryptedPreferencesMigration` is a one-way compatibility reader. The repository also documents that ordinary SharedPreferences is not an accepted production authentication fallback.

The remaining architectural recommendation is to keep all new security state on `SecureKeyValueStore` and remove compatibility constructors once old installations no longer require migration. No destructive migration change was made.

### 35. Database passphrase RAM wipe

The specific finding is not applicable to the current checkout. `AppDatabase.getDatabase()` creates a standard Room database and does not receive a SQLCipher passphrase or `SupportFactory`. Consequently, the cited `VVFApplication` passphrase allocation and post-construction wipe do not exist here.

If encrypted database support is introduced later, the passphrase must be created as a mutable byte array, passed only through the supported SQLCipher API, and wiped in a `finally` block after the library’s retention behavior has been verified. A byte-array wipe alone must not be presented as complete RAM erasure.

## Verification

Static verification confirmed that the current source contains no `memoryKeyMap`, no production raw-key fallback matching the cited pattern, and no SQLCipher passphrase construction. The Keystore capability method is implemented against the Android Keystore key factory and returns a nullable device-reported result.

Android Gradle tests and lint require an Android SDK, which is not installed in the sandbox used for this review. The repository’s GitHub Actions Android runner remains the appropriate environment for full unit, instrumentation, lint, and release verification.

## Conclusion

The findings were evaluated against the actual checkout rather than treated as automatically true. The confirmed hardware-backing gap was fixed with runtime evidence collection. Existing lockout and secure-store controls were preserved, while the absent memory-key fallback and absent database-passphrase lifecycle were correctly classified as not reproduced or not applicable.
